# Known Limitations

Three deliberate tradeoffs in the Glutenia backend, each identified during an engineering audit of the codebase and left in place rather than rushed under a defense deadline. Each is a known, bounded limitation with a clear path forward — not an oversight.

## No pagination on list endpoints

Every list endpoint in the API (`GET /products`, `GET /recipes`, `GET /orders` for admins, `GET /events`, and others) returns the full collection in a single response — there is no `limit`/`skip` or cursor-based pagination anywhere except two endpoints that hardcode a small cap (notifications at 50, scan history at 20). This exists because the project's data volumes are demo-scale: a few dozen to a few hundred documents per collection, so an unbounded query returns in milliseconds and the response body stays small. Implementing pagination properly is not a backend-only change — it means adding query parameters and response metadata (total count, page info) on the server, and updating every corresponding list screen in the mobile app to request pages and handle infinite scroll or "load more," which is real, cross-cutting work touching both codebases. Given the deadline, the tradeoff was to ship a correct, simple, unbounded API now and treat pagination as the first thing to add if the product ever needs to handle real user volume, rather than build a half-finished paging mechanism that neither the API nor the client fully exercises.

## Product and establishment images stored as base64 inside MongoDB documents

Uploaded images (product photos, establishment cover photos) are stored directly inside their MongoDB document as a base64-encoded data URI, rather than uploaded to object storage (e.g. Amazon S3, Cloudinary) with only a URL saved to the database. This exists because it requires zero external services, zero additional cost, and zero extra configuration — multer already handles the upload in memory, and converting the buffer to a data URI is a one-line change with nothing else to provision, which mattered for a project built and hosted on a student budget. The real fix is to upload the file to object storage on receipt and store only the resulting URL on the document, which keeps documents small, lets images be served through a CDN instead of the API process, and avoids MongoDB's 16MB document size ceiling ever becoming a real constraint. It was deprioritized because it's an infrastructure dependency, not a code change — it means creating and paying for (or provisioning a free tier of) a storage bucket, wiring up credentials, and handling the upload/serve flow around it, which is a reasonable next step once the project needs to host more than demo-scale image volume, not before.

## JWT role is not re-validated against the database after issuance

A user's role (`customer`, `professional`, `admin`) is embedded in their JWT at login and never re-checked against the database on subsequent requests — authorization middleware trusts whatever role the token carries. This exists because it's the standard behavior of a stateless JWT: the whole point of not looking up a session on every request is that the token itself carries everything needed to authorize it, and re-querying the database on every request to double-check a role would give up that benefit while only protecting against a scenario (a role changing mid-token-lifetime) that doesn't currently have any code path that triggers it — there is no "demote this user" feature in the app today. The real fix, if role changes become a real feature, is either short-lived tokens paired with a refresh-token flow (so a revoked/changed role takes effect within minutes rather than up to the current 7-day expiry), or a server-side token blacklist checked on each request, both of which add real complexity and a small latency cost to every authenticated request. It was deprioritized because implementing revocation infrastructure for a threat that has no current trigger would be solving a problem the app doesn't have yet, at the cost of complexity it would carry everywhere.
